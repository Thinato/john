# John — dev notes

- **Knowledge base first: before any work, read it; add to it when you learn something.** Start every task with `ls kb/notes/` and `python3 kb/kb.py query "<the task>"` (plus a query per area you will touch), and keep using it while you work. It searches the notes in `kb/notes/` and the code (needs `VOYAGE_API_KEY`; without it, grep `kb/notes/`). When you learn something non-obvious about the codebase (a user correction, a gotcha, a pitfall, a confirmed approach), write or update a note in `kb/notes/` in the same PR; format and rules in `kb/README.md`, checked by `python3 kb/kb.py check`.
- Workflow: issues in GitHub, one branch + PR per issue, `main` is PR-only with required CI. Follow CONTRIBUTING.md (branch names, definition of done, labels).

- Build: `cmake --build build`; test: `ctest --test-dir build --output-on-failure` (core tests: `TEST(name)` in `tests/core/<area>.cpp`, `build/john-tests <name>` runs one; tests/mcp_smoke.sh drives the server).
- One shared core (`john_core`: one `.cpp` + header per area: song, theory, catalog, analyze, settings, i18n, sound, abc/musicxml, transcribe/import_audio) used by both executables. Put logic there, not in the GUI or MCP files. Which file a change goes in, its test file and its strings file: `kb/notes/where-things-go.md`. Keep to your area's files so parallel branches don't collide.
- Bar/beat numbers always come from `positions()`. Accidental display always comes from `accidentals()`. Don't re-derive them.
- The MCP server speaks the initialize-based protocol (2024-11-05 .. 2025-11-25). It answers unknown methods (e.g. `server/discover`) with -32601, so modern clients fall back to `initialize`.
- Nothing but JSON-RPC may be written to the MCP server's stdout.
- Viewer text goes through `tr()`/`trf()`/`L()` with the English as key, plus an entry in the matching `i18n/pt-BR/<area>.json` (the core test checks every key and duplicates). MCP output stays English: only the GUI calls `setLanguage()`.
- Audio: all music logic (play order, schedule, synth, YIN) lives in core `sound.cpp` and is tested offline. `audio.cpp` only does device I/O. Never play sound or open the mic during automated checks; render to a buffer instead (see the pitch tests in tests/core/sound.cpp).
- Check GUI changes visually with `JOHN_HOME=<tmp> JOHN_SNAPSHOT=<tmp>/s.tga ./build/john`, then convert with `sips -s format png`. Never take full-screen screenshots.
- Audio transcription (`transcribe.cpp`): harmonic-summation salience, octave-ghost suppression, Viterbi melody line, ornaments (short graces become cut/tap/roll candidates on the main note), continuity filter (octave errors, accompaniment), Ellis beat tracking, sixteenth grid with eighth triplets per beat and swing straightened (#2). Test MP3s go in `tmp/` (gitignored, copyrighted). To tune it, `JOHN_TRANSCRIBE_DEBUG=<file>` dumps the per-frame track (time, chosen MIDI, confidence, top 3 candidates, onset flux). Check every change against the synthetic mix test in tests/core/transcribe.cpp, then by ear on real songs.
