# Translating the viewer (tr, i18n/<code>/*.json)

## Context
Adding or changing any text the viewer shows (`src/gui_*.cpp`, and the core text it displays: `keyName()`, `durationName()`, `defaultTechniques()`, instrument and folder names), or adding a language (#23). Code: `src/i18n.hpp`, `src/i18n.cpp`, the files in `i18n/<language>/`.

## Rule
The English text is the key: `tr("Play")` returns the translation from the current language, or the English when there is none. `trf("%s (song)", name)` translates then formats (printf, checked by the compiler against the English). A widget label uses `L("Folder")` (see gui-imgui-id-translated-labels). A language is one folder `i18n/<code>/` of `.json` files, merged by `loadStrings()` (`"English": "translation"` pairs, one file per area, plus `"@language": "its own name"` for the Settings combo, in pt-BR's `gui.json`); desktop reads it from `i18n/` next to the executable (release package) or else the source tree (`bundled("i18n", JOHN_I18N)`), the web bundles `i18n/` with a `--preload-file`. The MCP server stays English because `setLanguage()` and `setSolfege()` are global state that only `main()` in the GUI calls; until then `tr()` returns its argument and `noteName()` gives letters.

## Why
gettext style needs no ids and no English file, and a missing entry can't break the UI. Core functions like `keyName()` and `durationName()` are shared with the MCP server (`listing()`, `analyze()`, `list_songs`), so they translate through `tr()` instead of the GUI translating at every call site.

## How to apply
New viewer text: wrap the literal in `tr()`/`trf()`/`L()` and add the Portuguese to the `i18n/pt-BR/*.json` file of its area (where-things-go); the core test fails if a literal `tr("...")`, `trf("...")` or `L("...")` in any `src/*.cpp` has no entry, if a key is defined twice, if a value is empty, or if its `%` conversions differ from the key's. Never pass `tr(...)` as the only argument of a printf-style ImGui call (`Text`, `SetTooltip`, `TextDisabled`): use `"%s", tr(...)`, since a `%` in a translation would be read as a format. Text built from data (folder names, `MODE_FMT`, duration names) is translated with `tr(variable)`: add those keys by hand. Automatic language: `systemLanguage()` reads `LC_ALL`/`LANG`, on macOS falls back to `CFLocaleCopyPreferredLanguages()` when both are empty (apps started from Finder get no `LANG`; this is why CoreFoundation is linked to `john_core` on Apple), and on the web reads `navigator.language`; `matchLanguage()` maps the result to a file (exact code, then the same base language, else "en") and is what the test covers, since the CF value can't be faked in a test. To try the macOS path: `env -u LANG -u LC_ALL ./build/john -AppleLanguages '(pt-BR)'`. Note names and key names are separate settings: `setSolfege(notes, keys)` from `Settings::solfege` and `Settings::solfegeKeys`. Keys (`keyName()`, and `tonicName()` for the whistle key in instrument names) use Do Re Mi only when a non-English file is loaded (`setLanguage()` returned true), so English always says "D major". The Settings checkbox for keys is hidden in English (`App::english`). Never call `setLanguage()`/`setSolfege()` from the MCP server (`src/mcp_*.cpp`) or core code. Song titles, notes and comments are not `tr()` entries: a song carries its own translations in its `"i18n"` map, shown with `songText()` (see song-translations-i18n-map, #47).
