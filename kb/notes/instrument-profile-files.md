# Instrument profiles: files, catalog, same results

## Context
Adding or changing an instrument, `struct Instrument`/`NoteLevel` in `src/john.hpp`, the catalog code in `src/song.cpp` (`parseInstrument`, `findInstrument`, `instruments()`, `saveInstrument`), `rangeCost()` in `src/analyze.cpp`, the Settings instrument editor in `src/gui_main.cpp`, or the MCP tools `list_instruments` / `define_instrument` / `delete_instrument` (#85).

## Rule
One JSON file per instrument; the file name is the id. Built-ins are `instruments/<id>.json` (found by `instrumentsDir()` like `lessons/` and `i18n/`, bundled on the web at `/instruments`); custom ones are `<data folder>/instruments/<id>.json` and a custom file with a built-in's id replaces it in place. Fields: `name`, `low`/`high` (written pitch, `"D4"` or a MIDI number), `octave`, `key`, `keys` + `keyed_name` (keyed instruments: the whistle/harp key moves the range by its pitch class above `keys[0]`), `notes` (semitones above `low` -> `"hard"`/`"impossible"` or `{level, how, weight}`; missing = easy), `techniques`, `instead` (technique -> a listed technique played in its place, #86), `sound` (a `SOUNDS` voice), `hints`, `order`. A file that fails `parseInstrument()` is skipped with a message in `instrumentWarnings()` (shown in Settings and by `list_instruments`). `rangeCost()` reads `Instrument::level()`: `out` counts notes out of range or impossible, `hard()` adds `weight * 10` per hard note.

## Why
The owner's decisions on #85: files can be shared, a broken one only drops itself, and one whistle/harp profile serves every key because the table is relative to the bottom note. The whistle's table reproduces `finger()`: half-holes weight 1, the cross-fingered C weight 0.2, so `hard()` is still `half * 10 + cross * 2`. The owner required the same results for every built-in except the harmonica; `tests/test_core.cpp` compares the old `findInstrument()`/`rangeCost()` (copied into the test) with the new ones over every whistle key and a pitch sweep. `RangeCost::weight` defaults to `half * 10 + cross * 2` so the existing literal `RangeCost{out, half, cross}` checks still mean the same.

## How to apply
Never hard-code an instrument list again: use `instrumentIds()` for instrument pickers and `SOUNDS` for playback voices (synth voices stay code). `findInstrument()` matches a whistle/harp key against `keys` case-insensitively and returns the listed spelling ("c" -> "C", "bb" -> "Bb"), because `whistleBase()` and old songs and settings accept lowercase; the same-results test sweeps lowercase keys too. Finger with `in.key`, never `song.whistle`. `saveInstrument()` runs the JSON through `parseInstrument()` first and checks every technique id against `loadTechniques()`, and throws, so the editor can't write a file the loader would skip; the editor clears `keys`/`keyed_name` when the key leaves that list. The catalog is cached behind a mutex and `findInstrument()` copies only the match (it runs per frame and per note); the GUI's `poll()` and every MCP tool call run `reloadInstruments()`, and the GUI judges every song again when `instruments()` changes. Songs write `instrument_name` only for non-built-in ids (`toJson` looks it up), so a deleted custom instrument shows "Written for: <name> (deleted)" (`instrumentLabel()`, the GUI's `writtenFor()`) and plays as the D whistle. Reset rule (owner, #85): only a real delete (`deleteInstrument()`, used by the GUI's Delete button and `delete_instrument`) resets a Settings instrument to the D whistle and saves it. A broken or missing custom file leaves `settings.json` and `App::set` alone; `myInstrument()` and the MCP server's `argsOrSettings()` read it as the D whistle meanwhile, so the user's choice comes back when the file does. Ids are file names: no Windows device names (`con`, `com1`, ...). `define_instrument` takes only its documented fields; `hints`, `order` and `keys` are for built-in files. Gate fingering charts on `Instrument::hints` (tin whistle charts fingered on `key`); the GUI's `instName()` translates built-in whistle/harp names from `in.key`, and a custom profile keeps its own name. Changing a built-in's table changes playability for everyone: update the same-results test only if the owner asked for the change.
